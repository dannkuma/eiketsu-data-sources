# Code Review Guidelines

## Purpose

本ドキュメントは、
Pull Request をレビューする際の判断基準を定義します。

レビューでは、
単なる好みやスタイル差ではなく、
実際に修正する価値がある問題を優先してください。

## Review Priority

以下の順序を意識してレビューしてください。

1. バグ
2. セキュリティ
3. データ整合性
4. ドメイン仕様との不整合
5. 認証・認可
6. Laravel / PHP の誤用
7. パフォーマンス
8. エラーハンドリング
9. テスト不足
10. 保守性

## Correctness

変更によって期待する処理が正しく動作するか確認してください。

特に以下を確認してください。

- 条件分岐の漏れ
- null の扱い
- 境界値
- Collection が空の場合
- Record が存在しない場合
- 状態遷移
- Return 値
- Transaction の一貫性
- 例外発生時の状態

## Domain Logic

ドメインルールに関係する変更では、
`docs/domain.md` を参照してください。

特に以下に関係する変更を重点的に確認してください。

- 武将
- 戦器
- 英魂
- 大判
- 所有状態
- 売却
- 購入
- 装着
- 強化
- ロック

コードだけでは仕様を判断できない場合は、
問題だと断定しないでください。

## Security

以下を確認してください。

- Authorization
- Authentication
- Input validation
- Mass Assignment
- SQL Injection
- XSS
- CSRF
- Sensitive information
- File upload
- External API input

特にユーザー所有リソースを変更する処理では、
対象リソースの所有権確認を確認してください。

## Database Integrity

データ更新処理では、
途中失敗による不整合が発生しないか確認してください。

必要に応じて Transaction の利用を確認してください。

特に以下の操作では注意してください。

- 残高変更
- 購入
- 売却
- アイテム付与
- アイテム削除
- 複数テーブルの更新

## Laravel

Laravel の利用方法として、
実際に問題がある箇所を確認してください。

例:

- FormRequest を使うべき複雑な validation
- 不適切な Authorization
- N+1
- 不要な Query
- Relationship の誤り
- Mass Assignment
- config を経由しない `env()`
- Controller に集中した大きな Business Logic

単なる「Laravelでは別の書き方もできる」
という理由だけでは指摘しないでください。

## Performance

以下のような実際に影響する可能性が高い問題を指摘してください。

- N+1
- ループ内 DB Query
- 不要な全件取得
- 大量データのメモリ展開
- 同じ Query の繰り返し
- 大量の外部 API 呼び出し
- 不必要な Browser 操作

小規模な処理に対する
根拠の薄いマイクロ最適化は指摘しないでください。

## Error Handling

失敗しうる処理では、
失敗時の挙動を確認してください。

特に以下を確認してください。

- 外部 API
- Stripe
- DB Transaction
- File I/O
- Browser Automation
- CSV Import / Export
- Network Access

例外を握りつぶしていないかも確認してください。

## Tests

変更内容に応じたテストが存在するか確認してください。

以下の場合は、
テスト追加の必要性を検討してください。

- 新しい Business Logic
- Bug Fix
- Validation 変更
- Authorization 変更
- 状態遷移変更
- 金額・残高変更
- DB 更新処理

ただし、
単純な View の微調整などに対して
機械的にテスト追加を要求しないでください。

## Maintainability

以下のような、
将来の変更を大きく難しくする実装を確認してください。

- 同一ロジックの重大な重複
- 責務が混在した巨大なメソッド
- 意味の分からない命名
- 過剰な密結合
- 既存設計から理由なく逸脱した実装

ただし、
単純なコードに対して過度な抽象化を要求しないでください。

## Review Comments

レビューコメントでは、
問題の具体性を重視してください。

可能な限り以下を説明してください。

1. 何が問題なのか
2. どのような条件で問題が発生するのか
3. どのような影響があるのか
4. 必要であれば修正方針

Bad:

> この処理はよくないです。

Better:

> この処理では `$user->balance` を更新した後に
> アイテム作成が失敗すると、大判だけが減った状態になります。
> 2つの更新を同一 Transaction 内で実行することを検討してください。

## Confidence

確証のない問題を断定しないでください。

仕様・呼び出し元・データ構造を確認しても判断できない場合は、
可能性として説明してください。

例:

> この値が null になる可能性がある場合、
> ここで例外が発生する可能性があります。

のように、条件を明確にしてください。

## Do Not Report

原則として以下だけを理由にレビューコメントを付けないでください。

- Pint が自動修正できるフォーマット
- 空白
- 改行
- インデント
- 個人的な命名の好み
- 同等な Laravel API の好み
- 実害のない軽微なリファクタリング案
- 根拠のないパフォーマンス懸念

コードを変更しなければならない明確な理由がある場合のみ、
レビューコメントとして指摘してください。

## Final Review Principle

レビューの目的は、
コメント数を増やすことではありません。

「この Pull Request をこのまま merge すると
実際に問題になる可能性があるか」

という観点を優先してください。
